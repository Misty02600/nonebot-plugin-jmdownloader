# ADR-0001：使用异步读写锁协调缓存生命周期

## 状态

已替代

## 日期

2026-07-31

## 当时遇到了什么

插件的图片工作目录、最终 PDF/ZIP、密码 sidecar 和待上传副本都位于同一个缓存根目录。原定时任务每天 03:00 直接执行 `shutil.rmtree()`，既不知道是否有 `JMService` 下载线程，也无法保护准备完成到 OneBot 读取文件之间的上传窗口。

现有输出路径锁只能串行化同一个最终文件，不能阻止外部清理删除整个根目录。与此同时，`asyncio.to_thread()` 的调用协程被取消时，已经开始的工作线程仍会继续访问缓存；如果锁随协程立即释放，同路径请求或清理就可能与遗留线程重叠。

当前部署约束是单进程，不要求跨进程协调。普通下载需要继续并行，缓存清理低频且可以等待，不要求“忙碌时立即跳过”。

## 最后决定

1. 共享 `JMService` 持有一个默认配置的 `aiorwlock.RWLock`；不启用 `fast=True`。
2. 四个下载 handler 获取读锁，并从调用 `prepare_*_file()` 前一直持有到 OneBot 上传结束。
3. 定时清理通过 `JMService.clear_cache()` 获取写锁，等待已有读者退出后在线程中删除和重建缓存目录。
4. 保留现有最终输出路径锁；统一顺序为“缓存读锁 → 输出路径锁”，禁止反向获取和锁升级。
5. 缓存相关同步操作使用 `run_sync_to_completion()`；调用方取消后先等待工作线程结束、清理未发布输出，再释放所有权并重新传播取消。

## 为什么这样选

- 读锁允许不同下载和上传继续并行，写锁准确表达“清理整个缓存必须独占”的语义。
- `aiorwlock` 已实现写者等待和读写状态管理，避免项目自行维护活动计数、维护状态、等待者唤醒和异常释放。
- 写锁等待比探测后跳过更符合每日清理目标；等待中的写者会限制新读者持续插队，清理不会长期饿死。
- 把上传包含在读锁内，弥合了服务返回文件路径到协议端实际读取之间的生命周期空隙。
- 等待线程真实结束后再释放锁，能够同时修复下载取消和清理取消的同类问题。

## 没有采用的方案

- 只使用最终输出路径锁：无法代表整个缓存根目录，也保护不了上传窗口。
- 用布尔值或活动下载计数探测忙碌后跳过：需要自行处理竞态、等待者、公平性、异常和取消，且上传也必须进入计数。
- 使用 `asyncio.Condition` 自行实现读写状态机：可以满足需求，但生产代码和维护不变量更多。
- 为每次请求创建完全隔离的缓存并原子发布：隔离最强，但需要重构上游 `Bd_Pid` 目录、缓存复用和上传清理，超出当前问题规模。
- 分布式锁或文件锁：当前不支持多进程共享缓存，没有引入相应复杂度。

## 带来的影响

- 有利：清理不会再删除活动下载或待上传文件；不同请求仍可并行；锁状态机由成熟依赖维护。
- 代价：增加 `aiorwlock` 直接依赖；四个上传 handler 必须遵守租约范围；取消和停机可能等待同步线程自然结束。
- 风险：若上游同步下载永久卡住，读锁和同路径锁也会持续占用；多进程共享缓存仍无保护。
