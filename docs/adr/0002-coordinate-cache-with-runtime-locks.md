# ADR-0002：用运行时锁协调缓存并采用标准线程调用

## 状态

已采纳

## 日期

2026-08-01

## 当时遇到了什么

ADR-0001 同时决定了两件事：用读写锁协调定时清理与活动文件消费，以及自行封装 `asyncio.to_thread()`，让协程被取消后仍等待工作线程结束。后续核查发现两者的必要性不同。

定时任务每天直接删除整个缓存目录，且 OneBot 会在服务返回路径后继续读取文件，因此读写锁和同路径锁对应真实并发。取消桥则没有当前触发源：项目没有主动超时或 `Task.cancel()`；NoneBot 2.4.4 使用 `CancelScope(shield=True)` 运行 Matcher，正常停机不会在下载中途取消 handler；APScheduler 的任务取消只发生在调度器停机阶段。

AnyIO 的线程接口可以处理 AnyIO 取消作用域，但不能等价拦截外部原生 `asyncio.Task.cancel()`。自定义桥为了一个当前不存在且库接口不能统一表达的场景，引入了独立模块、重复取消循环、清理分支和专项测试。

## 最后决定

1. 继续使用一个 `aiorwlock.RWLock`：下载和上传持有读锁，定时清理持有写锁。
2. 继续用最终输出路径锁串行化同一文件的验证与生成；不同路径保持并行。
3. 固定锁顺序为“缓存读锁 → 输出路径锁”，禁止反向获取和读锁升级。
4. 同步 jmcomic、文件验证和目录删除直接通过标准 `asyncio.to_thread()` 执行，不维护自定义取消桥。
5. 当前不承诺主动取消或超时下载。未来新增此能力时，必须重新定义线程、文件清理和锁释放语义，并以新 ADR 替代本决定。
6. 缓存不保存密码 sidecar；用当前密码实际打开 PDF/ZIP，直接决定复用或重建。

## 为什么这样选

- 读写锁保护的是每天都会发生的清理与下载/上传并发，仍有明确收益。
- 同路径锁避免相同 ID 的并发请求重复生成和互相覆盖，同时不会串行化不同内容。
- `asyncio.to_thread()` 与项目当前 asyncio 运行栈一致，关键字参数支持也比 AnyIO 的接口直接。
- 删除取消桥使锁语义只描述当前运行路径，不为假设场景维护额外状态机。
- 实际文件验证已经能识别密码变化、加密开关变化和损坏缓存；sidecar 指纹是重复判断。

## 没有采用的方案

- 保留 `run_sync_to_completion()`：能覆盖原生任务取消，但当前没有调用方需要这一保证，维护成本高于收益。
- 全面改用 `anyio.to_thread.run_sync()`：与 NoneBot 兼容，但没有简化普通线程调用，也不能覆盖 APScheduler 使用的原生任务取消。
- 删除读写锁，只在清理前探测活动下载：探测与删除之间存在竞态，且难以覆盖上传期间的文件消费。
- 删除实际文件验证，只依赖配置指纹：无法发现损坏输出或上游未真正加密的文件。

## 带来的影响

- 有利：保留实际并发安全，删除取消桥、sidecar、指纹、原子状态写入及相关测试；密码变化仍会在下次准备时自动重建。
- 代价：若未来某个调用方直接取消正在等待工作线程的任务，线程可能在协程退出后继续运行；在增加此调用路径前必须先补充设计。
- 风险：所有锁仍只在单进程内生效；强制结束进程可能留下半成品，下一次实际文件验证会将其判为无效。
